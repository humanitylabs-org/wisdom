## Proven source barriers

- `Wisdom.load()` did not assign any `data` until the full `/api/wisdom` request returned, even when `WizOffline.projected()` already had the complete library and pending edits locally.
- The full endpoint holds `library.LOCK` while traversing all enabled archives and hydrating every chapter. `glosses()` then traversed the complete catalog again.
- Verified archive bytes have a four-bundle LRU. More than four enabled bundles can repeatedly evict each other. Every artwork owner lookup also traversed the full catalog; this amplified verification and decompression.
- `WizardApp.ready()` is not awaited by the app. The shared parser-blocking script remains unchanged: it is a separate possible transport bottleneck, not an established cause of this complaint.

Read-only HEAD probes against the real running process returned full-state times of **1.205, 1.208 and 1.092 seconds** on the VPS. HTML was 4.4ms, app JS 2.7ms, reader JS 5.7ms and offline adapter 1.8ms. Shared app-client retrieval was 6.1ms in an earlier direct sample and 1.7ms in a later sample. These are server-local samples, **not** the owner's phone timings and **not proof that the entire reported five-to-ten-second delay is explained**. No owner library response body was read. The admitted browser harness separately records genuine remote shell/app static delivery and frame attachment under a synthetic private-API barrier; its unmodified-live-static case must not be confused with the injected backend-delay regression.
